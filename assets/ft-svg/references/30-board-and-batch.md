# 30 · 看板与批量运维

> 面板是「可视化验证」的入口，不是另一套系统：**面板上每个按钮都有一条同构的 CLI 命令**，
> 底部提示块会把它列出来。这份文档说明看板怎么读、批量动作怎么做、
> 以及出错时先看哪里。

## 1. 路由（可分享、可后退）

| 路由 | 页面 |
| --- | --- |
| `#/svg` | 看板：整库图标 + 规范状态一屏看全 |
| `#/svg/group/<组路径>` | 分组页：这一支有哪些图标、做得怎么样 |
| `#/svg/asset/<组路径>/<名>` | 资源页：一枚图标的全部风格 + 编辑器 |
| `#/svg/asset/<组路径>/<名>/full` | 整页预览：放大看线帽、拐点、网格 |

分组路径里的斜杠照常写：`#/svg/group/ui/icons/nav`。解析规则是
「首段是类型标记，末段是资源名，中间剩下的拼回分组路径」，
所以 URL 一直是可读的，也能直接贴给别人。

## 2. 看板怎么读

```
工具条   搜索 + 标签筛选 + [新建分组][新建图标][批量导入][批量导出][规范自检][一键归一化]
统计条   2 分组 · 13 图标 · 12 合规 · 1 待规范 · 5 问题         24pt · stroke 1.8 · currentColor
分组区   ui/action  7 枚 · 1 待规范                [自检][归一化]
         ┌────┬────┬────┬────┐
         │ ✓  │ ↓  │ ✎  │ ⭐⑤│   ← 只有异常才挂角标
         │勾选│下载│编辑│星标│
         ├────┼────┼────┼────┤
         │check│download│edit│star-bad│  ← 目录名（CLI 里用的那个）
         └────┴────┴────┴────┘
底部     AI 批量运维等价命令
```

几个刻意的设计，读的时候别误判：

- **合规的图标不挂角标**。13 枚里 12 枚都标「合规」是没有信息量的噪音；
  只有「待规范」和「多风格（脚注里的 `×2`）」才标出来。
- **`待规范 N` 用墨色下缘线而不是红色**。它表示「需要看一眼」，
  不是错误；真正阻断的问题（无根元素 / 空图形）才会用 `--bad`。
- **数字卡片里「待规范」下的那条墨线**是唯一的强调手段——
  这个界面的语义色只有一个，靠对比度而不是颜色喊人。
- 统计条里的「已筛掉」只在有筛选条件时出现，告诉你有多少被挡在外面。

**待规范 = 当前风格不合规。** 一个资源有多个风格时，看板只审计 `activeStyle`。
所以会出现「看板上标着待规范，点进去资源页却说这一版合规」——那是因为
你正在编辑的风格不是当前风格。`svg style switch <组> <名> <风格>` 可以改。

## 3. 资源页

从上到下五块：

1. **面包屑 + 动作条**：整页预览 / 编辑历史 / 按规范修复 / 保存（有未保存改动时显示 `保存 *`）
2. **身份卡**：图形、展示名、路径、标签、风格数、整体合规状态
3. **风格对比**：所有风格并排，各自显示图形 + 合规状态 + 历史条数。
   边框加重的那张是**当前编辑目标**（点一下即切换）；标着「当前」的是**当前风格**（面板与看板默认展示它）
4. **编辑器 + 实时预览 + 规范问题**：三槽位（SVG / CSS / JS），`Ctrl/Cmd+S` 保存；
   右侧实时预览按 62% 居中渲染，规范问题逐条列出并给出修法
5. **CLI 命令块**：这一枚图标对应的 `cat` / `put` / `spec check` / `spec fix` / `detail`
   五条命令，参数已经填好，可直接复制执行；下面还有一段 `<<'EOF'` 的写回模板

「风格」和「当前风格」的区别值得再强调一次：

- **风格**（style）＝ 同一枚图标的并存实现，用于 A/B 对比，数量不限
- **当前风格**（activeStyle）＝ 看板与默认预览展示哪一个

## 4. 整页预览

`#/svg/asset/<组>/<名>/full`，或资源页点「整页预览」，或看板图标格右上角悬停出现的「全页」。

- **尺寸阶梯** 24 / 32 / 48 / 96 / 192 / 384 —— 24 是设计尺寸，16 是常见渲染尺寸，
  384 用来看清曲线拐点
- **底色** 白底 / 浅灰 / 深色 —— 切到深色是为了验证 `currentColor` 真的生效：
  如果某个图标在深色底上没变白，说明它写了死颜色（`spec check` 也会报 `hardcoded-color`）
- **24pt 网格** 叠加每格 1pt 的参考线 —— 用来核对关键线：方形应落在 `3→21`，
  圆形 `r=10`，坐标应落在整数或 `.5`
- **复制源码** 一键拿走当前风格的 SVG 本体

## 5. 批量导入

```bash
node bin/ft.mjs svg import <组> --from <目录> [--style default] [--tags a,b] \
    [--recursive] [--label-from filename|title] [--dry-run]
```

面板上的「批量导入」是同一个流程的两段式：**先填目录 → 再填目标分组 → 看计划 → 确认**。

行为要点：

| 项 | 行为 |
| --- | --- |
| 分组不存在 | 自动创建（报告里会写「分组为本次新建」） |
| 展示名来源 | `--label-from title`（默认）= 取 SVG 里的 `<title>`，取不到退回文件名；`filename` = 直接用文件名 |
| 资源名来源 | 文件名去扩展名，非法字符替换为 `-`（不追求好看的 slug，只求稳定寻址） |
| 已存在同名资源 | **跳过**并如实上报，不覆盖 |
| 目录里派生出的重名 | 导入前就整批拒绝（大小写不敏感的文件系统上很常见），不会静默丢文件 |
| 子目录 | 默认不加 `--recursive` 只扫一层 |

**导入是逐字节搬迁，不改内容。** 要改内容请用 `svg spec fix`——
那是显式的、会进编辑历史的动作；transfer 只搬不改，否则「导出再导入」就不是恒等变换了。

## 6. 批量导出

```bash
node bin/ft.mjs svg export [<组>] --to <目录> [--style <风格>] [--board] [--force]
```

产出「目录 + 一张自包含的 `index.html` 看板页」——图标按分组落到子目录，
`index.html` 把整组内联渲染出来，没有任何外部依赖，可以直接打包交接或丢进浏览器看。

| 项 | 行为 |
| --- | --- |
| 不传 `<组>` | 导出整库 |
| 不传 `--style` | 各资源各取当前风格 |
| 同名文件 | **默认跳过**并列出（导出器不改写别人的文件），`--force` 才覆盖 |
| 风格 svg 槽位为空 | 跳过并写明原因 |
| `--board` | 默认开；`--board=false` 只出 `.svg` |

## 7. 规范审计与归一化

```bash
node bin/ft.mjs svg spec show                 # 规范全文 + 合规骨架
node bin/ft.mjs svg spec check [<组>]         # 逐条列出不合规的图标与原因
node bin/ft.mjs svg spec fix [<组>] --dry-run # 先看改动清单
node bin/ft.mjs svg spec fix [<组>]           # 确认后写回
```

`<组>` 可省略 = 整库（`check` 与 `fix` 一致）。

面板上是「规范自检」（弹窗列出每条问题）与「一键归一化」（先弹计划确认框，
确认后才写回，完成后给结果面板）。**两段式不是多余的谨慎**：
批量改上百个图标是不可逆操作，而 `spec fix` 会占掉编辑历史的名额。

`spec fix` 的三条边界，遇到时不要当成 bug：

1. **长宽比不一致就拒绝迁移** `viewBox`，并保留原值 + 说明原因（强行等比缩放会把图形压扁）
2. **阻断级问题（`no-root` / `empty`）修不了**，会进 `failed` 列表而不是静默跳过
3. **只修「当前风格」或 `--style` 指定的那一个**，不提供「全库所有风格」——
   那等于把一套设计稿里刻意保留的对比版本一起抹平

## 8. 失败排查表

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 导入报「目录不存在或不可读」 | 路径写错，或不是本机可达路径 | 用绝对路径；确认目录里有 `.svg` |
| 导入报「多个文件派生出同名资源」 | `Foo.svg` 与 `foo.svg` 在 Windows/macOS 上会撞 | 改名后重导 |
| 导入后展示名是文件名不是中文 | 没加 `--label-from title`，或 SVG 里没有 `<title>` | 补 `<title>` 再导，或导入后 `svg rename` |
| 导出报告「跳过：文件已存在」 | 目标目录有旧文件 | 换个新目录，或 `--force` |
| 导出报告「跳过：风格 X 的 svg 槽位为空」 | 该资源还没写代码 | 先 `svg put` 写内容 |
| 看板标「待规范」，资源页说合规 | 看板审计的是**当前风格** | `svg style switch` 切到那个风格 |
| `spec fix` 报「viewBox 保持…（长宽比不一致）」 | 图形不是正方形（如 `0 0 32 16`） | 需人工决定：重画成方形，或接受不合规 |
| `spec fix` 的 `failed` 里有条目 | 阻断级问题：没有根元素 / 没有图元 | 补图形，自动修不了 |
| 面板改完，CLI `cat` 读到的还是旧的 | 面板的改动**只在点保存后**落盘 | 点保存（或 `Ctrl/Cmd+S`） |
| 面板看到的内容和 `cat` 不一致 | 两边看的是不同风格 | 资源页顶部的风格对比里确认当前编辑的是哪个 |

## 9. 面板与 CLI 的等价关系

不需要背两套东西。规则只有一条：**面板上出现的每个动作，底部 CLI 提示块里都有对应命令**。

- 看板底部的「AI 批量运维」列出库级命令（board / import / export / spec check）
- 资源页的「CLI 命令」块给出带**当前上下文参数**的命令（具体到某个组、某个名、某个风格）
- 更下方是完整的同构命令清单，加 `--json` 就是 agent 可以直接消费的形态：
  `node bin/ft.mjs routes --json`

给 agent 用的时候，**优先把资源页那段命令块原文交给它**——参数已经填好，
比让它自己拼 `svg put <组> <名> --style <风格> --code -` 可靠得多。
