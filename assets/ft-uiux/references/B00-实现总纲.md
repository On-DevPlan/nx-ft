## 实现参考的统一原则

| 原则 | 说明 |
| --- | --- |
| **A 是评、B 是写** | A 序列讲「项目审美基准与评分」，B 序列讲「代码骨架与落地」 |
| **B 必须可被 A 反向验证** | 每个 B 实现参考末尾给出「与 A 评分标准的对照表」——验证实现是否真的达标 |
| **B 不重复 A 的判定逻辑** | B 只给最小代码骨架，不重复 A 已经说过的话 |
| **B 的代码以 React + Vite 为准** | 本项目技术栈固定，跨框架的「通用实现」不属于本 skill 范围 |
| **B 的代码需通过本项目 lint 与分层规则** | 详见脚手架 skill `server-cli-web-scaffold` 的 A01 与项目 `eslint.config.js` |

## 实现工作流（主 agent）

1. 收到「实现 / 重构 / 评审某个面板」任务
2. **第一步（强制）**：调用 sub-agent 跑 [[A00-审核总纲]] 的 SOP —— **先用 A 评分维度检查现状**，知道「离项目审美基准差多少」
3. 根据 A 评分报告列出「需要做的 B 实现项」
4. 按 B01~B08 加载对应实现参考，写代码
5. 写完后再调一次 sub-agent 跑 A 评分 SOP —— **验证实现后是否真的达标**
6. 通过 = 交付；不通过 = 回到第 3 步

> **关键**：
> - **A 评分 → B 实现 → A 评分**，这是「A→B→A」闭环；
> - **不允许跳过 A 直接 B**（评审就是「先知道差多少、再动手」）；
> - **不允许只 B 不回头 A**（写完必须再评一次）。

## 与 A 序列的协作边界

| 边界 | A 序列 | B 序列 |
| --- | --- | --- |
| 写代码 | 不允许 | 允许 |
| 评代码 | 允许 | 不允许 |
| 评「项目审美匹配度」 | 核心 | 不涉及 |
| 给代码骨架 | 不涉及 | 核心 |
| 触发谁 | sub-agent（评分 SOP） | 主 agent（落地实现） |
| 时机 | 实现前 + 实现后 | 仅实现阶段 |

## 实现参考的最小骨架（每个 B0X 必含）

```
B0X · <主题名> 实现参考

## 实现目标（对应哪个 A 评分维度）
## 代码骨架（React 组件 / hook / util）
## 关键 props / state
## 与其它 B 的衔接
## 与 A 评分标准的对照表（反向验证）
## 测试要点
```

## 反模式

| 错误做法 | 后果 | 正确做法 |
| --- | --- | --- |
| 跳过 A 直接写代码 | 不知道离项目审美基准差多少，写完才发现跑偏 | 先 A 评分 → 再 B 实现 |
| 只写不评 | 不知道实现是否达标 | 写完后再 A 评分 |
| B 实现里塞评级标准 | 角色错乱 | B 只给代码骨架 |
| A 评分里塞代码骨架 | 角色错乱 | A 只给评分标准 |
